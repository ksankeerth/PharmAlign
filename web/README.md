# web

The PharmAlign UI: five views (Platform Admin, Process Owner, Case Officer, Decision Maker, Auditor) over the server contract in `../contracts/openapi/server.yaml`. It always talks to the server, so start the server first (see the repo README, or `scripts/dev.sh start`).

React 19, Vite, TypeScript (strict), react-router-dom 7, plain CSS with design tokens. No UI library. Fonts are bundled (IBM Plex Sans and Mono), so it works offline.

All company, product, case and person data is synthetic and marked so in the UI.

## Run

```
npm install
npm run dev            # http://localhost:5180, forwards /api to the server
```

| Script | Does |
|---|---|
| `dev` | Vite dev server |
| `build` | Typecheck, then production build to `dist/` |
| `typecheck` | `tsc` only |
| `test` | Vitest: the pure rules the screens use (`src/**/*.test.ts`) |
| `smoke` | Playwright against a seeded local server: opens `/` and every route, fails on any console error or error state |
| `e2e` | Playwright scenarios in `e2e/scenarios/`: the demo cases and rules, driven through the real screens against a seeded local server (see the repo README) |
| `e2e:all` | All four scenario specs, in two runs |
| `sweep` | Playwright: every route at desktop light, desktop dark and 768 px (console errors, error states, page overflow, axe), plus keyboard use. Screenshots go to `SWEEP_DIR` (default: the system temp folder), never into the repo |
| `gen:api` | Regenerates `src/api/schema.ts` and `src/api/operations.ts` from the server contract |
| `check:copy` | Fails on internal working terms, priority labels, decision references or any Arabic script in `src/`, `e2e/`, `public/` and docs |

The UI calls the server at the same origin (or `VITE_API_BASE`); in development Vite forwards `/api` to `PHARMALIGN_API` (default `http://localhost:8000`).

TypeScript is 5.9 because `openapi-typescript` needs the classic compiler API.

## Layout

```
src/
  api/             typed client, generated types, errors, transport
    schema.ts        generated by openapi-typescript (do not edit)
    operations.ts    generated: method, path, allowed views, simulation-only, per operation
    types.ts         friendly model names (CaseDetail, CheckDetail, ...) and operation helpers
    client.ts        one function per server operation
    errors.ts        ApiError (RFC 9457 problem, GuardProblem with `failed`)
    transport.ts     http calls and server-sent events
    events.ts        change bus: reloads open views after any mutation
  app/             shell: Shell, TopBar, navigation per view, session, theme
  components/      shared components (index.ts exports them all)
  hooks/useApi.ts  useApi and useMutation
  lib/             format, labels, jsonDiff
  pages/<area>/    screens, one folder per area
  routes.tsx       the route table: every screen in one place
  styles/          tokens.css, base.css, components.css, shell.css
scripts/           gen-operations, check-copy
e2e/               Playwright: smoke, scenarios/, sweep, keyboard
```

### Add a screen

1. Create `src/pages/<area>/MyPage.tsx` with a default export.
2. Add a row to `ROUTES` (or `CASE_TABS`) in `src/routes.tsx`, with `sample` (a concrete URL using demo ids) and `as` (a demo person who may open it). The smoke test then covers it.
3. If it belongs in a view's navigation, add it to `src/app/navigation.ts`.
4. The sweep and keyboard tests pick the route up from the table; add a scenario to `e2e/scenarios/` if it enforces a rule.

Inside the case page, tab pages render below the case header: don't render a second `PageHeader` there.

## Calling the API

```tsx
import { api, ApiError, type CheckDetail } from "../../api";
import { useApi, useMutation } from "../../hooks/useApi";

const { data, error, loading, reload } = useApi(() => api.getCheck(id), [id]);
const confirm = useMutation((fp: string) => api.confirmCheck(id, { fingerprint: fp }));

try {
  await confirm.run(data.fingerprint);
} catch (e) {
  if (e instanceof ApiError && e.isGuardProblem) {
    e.failed;              // every failed guard, render with <GuardList guards={e.failed} />
    e.currentFingerprint;  // what the server holds now, when a fingerprint was stale
  }
}
```

- Function names follow the contract's summaries (`listCases`, `getSigningPackage`, `signDecision`, ...); each line in `client.ts` notes its operationId.
- Response types are complete: every field the server always sends is present. Request bodies keep the contract's optional fields.
- `useApi` reloads by itself after any mutation, background completion, person or workspace switch.
- `api.sendAssistantTurn(...)` is an async iterator of server-sent events.
- `ConfirmModal` runs an action and shows a 409's guards inside the dialog.

## Demo people

**Switch person.** Use "View as" in the top bar (it keeps the screen when the other person has the same view, and goes to their home screen otherwise), or add `?as=<personId>` to any URL, for example `/cases/CASE-1053/signing?as=p-noor`. People ids: `p-jordan`, `p-sam`, `p-priya`, `p-alex`, `p-chris`, `p-dana`, `p-noor`, `p-robin`.

**Reset the demo data.** Use Platform Admin › Demo (type RESET), or `scripts/dev.sh restart --reseed`. Each browser spec resets through the server by itself, so a run needs no reseed or restart.

## Design

Tokens in `src/styles/tokens.css`: cool greys, one deep teal accent, semantic colours only for pass, look, held and error. Light and dark follow the system; Settings in the top bar picks one. Focus is always visible, motion respects reduced-motion, numbers are tabular, and the layout holds at 768 px (navigation becomes a drawer).
